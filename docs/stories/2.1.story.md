# Story 2.1: Adapter Interface & Registry

**As a** developer,
**I want** a clear API to define and register MCP tools,
**so that** I can extend the agent’s abilities safely.

## Acceptance Criteria

1.  An adapter interface for MCP tools is documented with TypeScript types.
2.  A registry loads tools at startup and validates their schema.
3.  Unit tests for malformed tool definitions are implemented and passing.

## Dev Notes

This story establishes the core extensibility pattern for the Sophos Agent. All work should be performed within the `src/lib/agent/mcp/` directory, following existing conventions.

### Technical Context from Architecture Docs:

*   **MCP Tool Interface**: The starting point is the `McpTool` interface defined in the coding standard. This should be formalized and expanded upon.
    *   `export interface McpTool<TArgs, TResult> { name: string; call(args: TArgs): Promise<TResult>; }`
    *   **Source**: `docs/architecture/coding-standard.md#mcp-tool-adapters`

*   **File Location**: New files related to the tool registry and interface should be created within `src/lib/agent/mcp/`. A new file, `registry.ts`, should be created for the registry logic. The interface can be defined in `index.ts` within the same directory to be easily exported.
    *   **Source**: `docs/architecture/source-tree.md`

*   **Type Safety**: All new code must be strictly typed using TypeScript. The use of `any` is forbidden.
    *   **Source**: `docs/architecture/coding-standard.md#language--type-system`

*   **Schema Validation**: The tool registry must validate the schema of each tool being registered. This can be done using a lightweight schema validation library like Zod, or by writing manual type guards. The architecture docs mention Zod for input validation at the edge, so it's a good candidate.
    *   **Source**: `docs/architecture/coding-standard.md#access--security`

*   **Testing**: Unit tests are required for the new functionality, especially for handling malformed tool definitions. A new test file `src/lib/agent/mcp/registry.spec.ts` should be created. The project uses Vitest.
    *   **Source**: `docs/architecture/coding-standard.md#testing-requirements`

## Tasks / Subtasks

1.  **(AC: 1)** **Define the Tool Adapter Interface**:
    *   In `src/lib/agent/mcp/index.ts`, define and export a comprehensive `McpToolAdapter` interface. It should include:
        *   `name`: `string` (unique identifier)
        *   `description`: `string` (for user-facing descriptions)
        *   `schema`: A Zod schema for validating arguments.
        *   `call`: `(args: TArgs) => Promise<TResult>`
    *   Reference `docs/architecture/coding-standard.md`.

2.  **(AC: 2)** **Implement the Tool Registry**:
    *   Create `src/lib/agent/mcp/registry.ts`.
    *   Implement a `ToolRegistry` class with the following methods:
        *   `register(tool: McpToolAdapter)`: Adds a tool to the registry. It should validate the tool's schema against the `McpToolAdapter` interface.
        *   `getTool(name: string): McpToolAdapter | undefined`: Retrieves a tool by name.
        *   `getAllTools(): McpToolAdapter[]`: Returns all registered tools.
    *   The registry should be a singleton instance, exported for use by the agent.

3.  **(AC: 2)** **Integrate Registry at Startup**:
    *   Modify the agent's startup process (likely in `src/lib/agent/index.ts` or a related file) to initialize the `ToolRegistry` and load any default tools (though none are required to be built in this story).

4.  **(AC: 3)** **Implement Unit Tests**:
    *   Create `src/lib/agent/mcp/registry.spec.ts`.
    *   Write unit tests for the `ToolRegistry`.
    *   Include tests for:
        *   Successfully registering a valid tool.
        *   Retrieving a registered tool.
        *   Attempting to register a malformed tool (e.g., missing name, invalid schema) and ensuring it throws an error.
        *   Getting all tools.
    *   Reference `docs/architecture/coding-standard.md#testing-requirements`.
