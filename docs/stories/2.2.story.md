# Story 2.2: Reference Examples: Memory & Fetch MCP

**As a** learner,
**I want** working examples of how the agent uses existing MCP tools,
**so that** I can understand tool invocation and how external capabilities integrate with reasoning.

## Acceptance Criteria

1.  The **Memory MCP** is demonstrated as a reference tool:
    - Example interactions show reading/writing memory entries.
    - Tool calls appear clearly in the reasoning trace.
2.  The **Fetch MCP** is demonstrated as a reference tool:
    - Example interactions show performing safe HTTP GET requests using the existing MCP adapter.
3.  No new MCP tools are introduced or implemented.
4.  Documentation includes:
    - A short “Using the Memory MCP” example.
    - A short “Using the Fetch MCP” example.
    - Both examples visible in the reasoning trace.

## Dev Notes

This story focuses on creating user-facing examples for the already-integrated Memory and Fetch MCP tools. The goal is to demonstrate how the agent uses these tools and how that usage is reflected in the reasoning trace.

### Technical Context from Architecture Docs:

- **Previous Story Insights**: Story 2.1 successfully integrated the `@langchain/mcp-adapters` and the `MultiServerMCPClient`. This story will build on that by using the already-configured client to interact with the `memory` and `fetch` MCPs.
- **Tool Invocation**: The agent should already be capable of invoking tools retrieved from the `MultiServerMCPClient`. This story is about creating the user-facing examples and ensuring the trace is clear. [Source: `docs/architecture/6-core-workflows.md`]
- **Reasoning Trace**: Tool calls should be visible in the reasoning trace. The trace is a `trace.jsonl` file in the session's log directory. The UI should also reflect these trace events. [Source: `docs/architecture/3-runtime-integration-details.md#3.6-markdown-persistence-layout`, `docs/architecture/coding-standard.md#logging--tracing`]
- **MCP Servers**: The `memory` and `fetch` MCPs are available as services in the Docker Compose setup. The agent connects to them via the `MultiServerMCPClient` configured in story 2.1. [Source: `docs/architecture/source-tree.md`]
- **File Locations**: Any new documentation or example files should be placed in a relevant location, perhaps a new `docs/examples` directory, linked from the main `README.md`. The task is primarily about demonstrating existing functionality, so code changes should be minimal, possibly limited to UI components for displaying the examples.
- **Testing Requirements**: While this story is about examples, any new UI components or modifications should be tested. Since this is about demonstrating existing functionality, end-to-end tests with Playwright are most appropriate to verify the examples work as expected and the trace is updated correctly. [Source: `docs/architecture/coding-standard.md#testing-requirements`]

## Tasks / Subtasks

- **Task 1 (AC: 1, 4): Create Memory MCP Example**
  - [ ] Create a simple prompt to demonstrate the Memory MCP.
  - [ ] The example should allow a user to write to memory, and to read from memory.
  - [ ] Verify that the `memory.write` and `memory.read` tool calls appear in the reasoning trace.
  - [ ] Add a "Using the Memory MCP" section to the documentation.
- **Task 2 (AC: 2, 4): Create Fetch MCP Example**
  - [ ] Create a simple prompt to demonstrate the Fetch MCP.
  - [ ] The example should allow a user to fetch from a URL.
  - [ ] Verify that the `fetch.get` tool call appears in the reasoning trace.
  - [ ] Add a "Using the Fetch MCP" section to the documentation.
- **Task 3 (AC: 3): Verify No New Tools**
  - [ ] Ensure that no new MCP tools are created. This story only uses the existing `memory` and `fetch` tools.
- **Task 4 (AC: 1, 2): E2E Tests**
  - [ ] Create a new Playwright test file for these examples.
  - [ ] The test should run through both the Memory and Fetch MCP examples, asserting that the UI updates correctly and the tool calls are made.
